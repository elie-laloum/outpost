Status: structure approved by the user; implementation prepared for review. The initial diagnosis and page inventory below record the decisions behind the changes.

## Audience and outcome

Developers who can run Node.js/TypeScript and use Git, but do not know Outpost. The Guide should provide a first inspected result, then task-focused help. Tutorials, how-to guides and explanations remain within Guide; exhaustive public contracts stay in API. CLI and YAML syntax without a corresponding public API contract remain clearly identified lookup material in Guide. No runtime feature changes, merge or publication are proposed.

## Findings

- There are 96 Guide pages in each language, currently arranged in 13 navigation groups. Both languages have matching page names, link targets and code-block counts; this structural parity does not establish semantic or runtime correctness.
- The initial sequence is useful, but complete examples precede common tasks in the sidebar. The development example has 28 named TypeScript files; readers meet dialogue, approval, checkpoints, loops and role restrictions together.
- `workspaces` combines source selection, Git integration, conflict resolution, mounts, publication and snapshots. `yaml-recipes` combines a first recipe, schema versions, local configuration, distribution, reports, secrets, harnesses and extensions.
- `typed-workflows`, `task-dependencies` and `first-workflow` overlap; progress/journals/recovery and security/isolation also repeat explanations. Context management and skill loading, or observation hubs and telemetry setup, have different reader goals.
- The setup builds `outpost:dev`, while the initial YAML configuration selects `outpost:latest`. The development example says a rejected approval ends as `failed`; `src/domain/workflow/termination.ts` distinguishes `rejected`. The checkpoint warning in `task-dependencies` points to `first-workflow` for a JSON projection that tutorial does not demonstrate.
- The profile and recipe-workflow examples under root `examples/` do exist in this commit. Their links are not missing-file defects. They nevertheless require cloning the source for a first offline result; make that prerequisite explicit or provide the usable example in the Guide. Do not create another examples tree.
- File-mode behavior is often appended after a page's Limits/API ending. Integrate it into the relevant task or link its dedicated guide, while retaining its implemented-but-unreleased status and live-validation limits.
- `yaml-components` is generated by `scripts/recipe-component-docs.mjs`. It currently exposes internal lot numbers and a component catalog without direct per-row API links. Update the generator if the approved design changes this page.
- Setup's reporting helper is required by the snippet checker, and the content checker currently bans console.log. Simplifying that learning prerequisite requires an explicit editorial/checker change, without reducing runnable-example validation.

## Proposed reading path

1. Install once, run one agent task, inspect the answer and branch.
2. Follow task-specific links to run checks, obtain typed data, continue a conversation or save a review report.
3. Connect two tasks, then learn dependencies, failures, retries and offline tests.
4. Add checkpoints and human input only when the workflow needs them.
5. Offer a separate first YAML recipe from the entry page; use the same image/prerequisites and keep recipe and execution configuration separate.
6. Keep agent/provider configuration, automation, storage and custom harnesses as goal-based branches, not required reading.
7. Put complete use cases after their prerequisite how-to material. Retain their executable assembly, not just conceptual fragments.

Use tutorial labels for the initial lessons, task-oriented titles for how-tos, and explicit explanation titles for lifecycle/security/storage. Keep the two Guide/API spaces and the current rendering components. The groups below are the proposed sidebar order; closed advanced groups keep the initial navigation focused.

## Planned extractions and redirects

- Keep `workspaces` as the source chooser. Add focused pages for Git branch work, checked integration/conflict resolution, working without Git, and publishing file outputs. Preserve source mount effects, rollback limits, snapshots and explicit recovery.
- Merge `typed-workflows` into `task-dependencies`; `observe-and-recover` into the progress/journals/recovery path; `isolation` into `security`. Redirect the retired pages in both languages.
- Extract recipe configuration, local extensions and recipe sharing from `yaml-recipes`. Keep recipe format and execution configuration versions distinct and CLI flags in `cli`.
- Extract signed approvals, HTTP queue exposure, OpenTelemetry export and harness skills where they serve independent tasks.
- Separate development planning and approval from implementation and verification, with explicit file dependencies and execution entry points for the complete use case.
- Preserve existing routes wherever possible. Add bilingual redirects for retired pages, review existing inbound anchors and update cross-links, home entry points, pagination assumptions, editorial guidance and affected validation expectations.

## API coverage before removal

Checked examples of existing coverage: `DiffGuard` already specifies rename/binary/line-count behavior; `Retry.maxDelayMs` describes the server minimum; `WorkspaceOutputOptions` describes destination-relative paths and selected deletions; `AgentConflictResolverOptions.verify` describes verification requirements and deadline. Link these contracts where needed instead of copying their full catalogs.

Coverage still needs completion before moving all detail: `createCronSchedule` mentions macro examples but does not list the complete supported macro mapping currently in the Guide. `publishWorkspaceOutputs` has a brief rollback summary but not the Guide's full non-atomic publication and concurrent-edit recovery explanation. Keep those consequences in the how-to and expand the maintained API source for any contract detail removed from it. YAML component mappings must point to the actual declaring contracts; API symbol pages must not become a substitute YAML manual.

Every extraction will be checked against `docs/reference-content/`, relevant source and tests, then regenerated through docs:sync. This audit is not a claim that every API field or example has already been validated.

## Implemented structure

The Guide now has 106 pages per language in 14 task-oriented groups. Thirteen focused pages replace sections of larger documents; three overlapping pages are merged with bilingual redirects. The homepage, setup, first task, first workflow and first YAML recipe share a README review as their initial outcome. Complete development examples come after their prerequisites; planning has its own runnable entry points.

The first examples print their result directly. Live reporting remains on the progress page. Shared files in the development tutorial are named in its prerequisites and assembled from their published source by the snippet checker, so splitting the tutorial does not hide imports.

Git branches, checked integration, file workspaces, file publication and remote synchronization have distinct destinations. Recipe configuration, local extensions and sharing are separate from the first recipe. Signed decisions, HTTP queues, OpenTelemetry and harness skills are optional task pages. The lifecycle page explains ownership without repeating runnable task examples.

Reference sources now include the complete cron macro/field syntax and the conditional rollback behavior of file publication. Existing declaring contracts cover the other removed option tables. Generated YAML component mappings link to public contracts and no longer expose internal implementation lots. Reference links for workspace families point to the focused Guide pages.

The legacy route manifest retains 914 redirects. `guide-anchor-moves.json` records 166 existing section bookmarks, including the homepage; the rendered-site check verifies both the retained anchors and their destinations. Existing links to moved sections point directly to their new location.
