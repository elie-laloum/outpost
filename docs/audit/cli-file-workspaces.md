# Validate native CLI file workspaces

This procedure validates one pinned adapter variant at a time. The live campaigns below establish capabilities per pinned adapter and file binding; all undeclared capabilities remain refused. Interactive evidence includes explicit non-secret onboarding and temporary-workspace trust preparation. Do not declare a capability from the code inspection, container preflight or synthetic tests below. Obtain the account owner's approval before running with `--live`: these commands make paid model calls.

The native request builders do not invoke Git themselves. Codex's native repository check and Copilot's persisted Git context are the explicit Git assumptions found in these paths. File reports have version 2 and publications appear in `fileOutputs`.

File dispatch now supplies a private capture home under that runtime for capture, lookup and restore. The regression in `test/functional/cli-file-workspaces.test.ts` reproduces the previous portable-retention refusal, verifies capture and archive containment, destroys the execution home, and restores into a fresh home. Its process emits synthetic events; it is not evidence of native Claude model behavior.

## Prepare a run

Use Node.js 24+ and a locally built Docker image containing the descriptor's exact CLI version. The script reads the catalog rather than maintaining another agent registry. It checks `--version` before any dispatch in every allocated sandbox and refuses mismatches. Each run exercises ephemeral, copy, read-only mount and writable mount bindings sequentially.

Start with the no-model preflight:

```sh
node scripts/cli-file-live.mjs claude --image outpost:claude --preflight
```

Choose an explicit model and authentication mode before requesting approval. Environment-key runs use only the selected descriptor variable and never read a host login file or run a credential login command. The subsequent account-session campaigns were explicitly authorized as an exception to the original environment-only restriction: `--auth account` uses the existing authentication plan, including guarded host reads and private temporary copies when required. Copilot selects its stored token into the environment; Kimi copies the selected region profile and runs its native login refresh; Antigravity copies its native OAuth token. Never read a system keychain or write credentials on the host. It disables execution logging, emits no raw agent output or error messages, and retains only validation metadata in its JSON report. Temporary files and captured conversations are removed after the run. No secret value belongs in a command line, committed evidence or log.

`--auth account` selects the native account model by default; the report records `model: null` rather than inventing a resolved model name. Kimi account runs accept `--region global|mainland-cn`. `--auth usage` selects the descriptor's API-key variable. `--auth account-token` is available where the descriptor declares an environment token, including Claude and Copilot. Codex's ordinary API-key plan invokes `codex login`; this validator instead selects its existing custom Responses-provider variant at `https://api.openai.com/v1` with an environment key. Evidence for that variant must not be presented as account-login validation. Kimi requires an explicit model. Antigravity's generated settings contain no key.

After approval, run dispatch first, then repairs:

```sh
node scripts/cli-file-live.mjs claude --image outpost:claude --model MODEL --auth account-token --suite dispatch --live
node scripts/cli-file-live.mjs claude --image outpost:claude --model MODEL --auth account-token --suite repairs --live
```

Replace `MODEL` with the approved model. The dispatch suite runs four CLI turns. The repairs suite runs a two-turn repair per binding, for eight CLI turns total. Each suite runs independently; `--suite all` combines them with continuation and live input. Use `--binding` to select a single binding when investigating a failure. Native CLIs can make multiple model requests within a turn; these counts are not billing caps. Each turn has a three-minute deadline and a one-minute idle limit. There are no automatic campaign retries. A failed assertion stops the campaign.

Dispatch must edit a seeded file, create another, return validated JSON, publish both through `fileOutputs`, and preserve or modify the source according to the binding. The repair validator rejects the first parsed answer with a new required value. A successful repair requires exactly two successful CLI turns sharing the conversation ID and the corrected typed value; accepting the first answer cannot count as repair evidence.

`--suite continuation` checks warm resume and, for agents that capture sessions, restore in a fresh container from runtime storage. Agents that support fork must also fork successfully with a distinct conversation ID, both warm and in a fresh container. The prompt asks for a random token given only in the original conversation. `--suite liveInput` injects a nonce-bearing instruction during a real tool call, requires delivery mode `injected`, checks the resulting file and typed response, and refuses any interrupt/resume or extra CLI turn. `--suite all` includes live input but excludes interactive; agents without a native live-input protocol must use the applicable suites separately. Antigravity can demonstrate only warm resume; this cannot justify a general portable-continuation declaration.

For the interactive suite, run the terminal driver from a real terminal on Linux with GNU `script` available:

```sh
node scripts/cli-file-terminal.mjs claude --image outpost:claude --model MODEL --auth account-token --suite interactive --live
```

It drives a real PTY, validates terminal stdin/stdout inside Docker, submits a follow-up through terminal input, verifies two file effects, exits the CLI, cancels a separate idle attachment and checks sandbox reuse. It keeps terminal output in bounded memory and prints only progress metadata. No terminal transcript is retained. For Claude, the suite prepares `hasCompletedOnboarding`, a theme, and trust for the owned temporary working directory in the private `.claude.json`; it merges existing preferences and writes no credential. Codex receives only a trusted-project entry in its private configuration. Other CLIs retain native trust and permission dialogs. The driver forwards operator confirmations when its prompt recognition cannot handle a native dialog. Kimi receives its first prompt through terminal input after the trust dialog, because its adapter intentionally refuses an initial interactive prompt. This is a prepared interactive variant, not proof that a fresh Claude home automatically completes its setup dialogs. Native tool permission confirmations remain active. In interactive reports, `turns: 2` counts the two user requests within the productive terminal session; the idle cancellation session makes no model request.

The script enables candidate `fileWorkspaces` fields only in its local harness binding. This is a validation instrument, not a consumer workaround. Production declarations stay in each adapter's own folder and must be added only after reviewing passing live evidence for the exact variant. Keep all undemonstrated fields absent.

## Record evidence and finish

The default report is a unique `/tmp/outpost-cli-file-*.json`; `--report` chooses a path. Reports identify the pinned version, image, model, credential mode, variant, source binding, checks, turn count, usage where available and cleanup status. Preflight reports are explicitly marked `preflight` and cannot justify declarations. Failed or incomplete cases cannot justify capabilities either.

After live validation, update each affected adapter, its deterministic gate tests, the bilingual working-with-files guide, the `AgentFeatures.fileWorkspaces` reference source and both changelogs. Record the evidence path and scope. Run `bun run docs:sync`, the relevant documentation checks, `bun run check`, `bun run coverage` and real Docker tests. Keep the validator out of routine tests and CI. Do not commit, tag or bump a version without a separate request.

The successful reports verify the pinned CLI in every allocated sandbox before dispatch and confirm temporary resource cleanup. Dispatch and repairs also validate JSON, new and edited files, publication through `fileOutputs`, version-2 reports, source reads and the expected source effects. Native capture is kept within the runtime directory; the repair evidence does not establish cold restore or fork.

The initial dispatch/repair campaign used 15 CLI turns in total. An initial two-turn campaign failed during copy verification; a one-turn diagnostic run localized the failure to the source-token comparison. The fixture now uses an explicitly newline-terminated token and requests that form. The complete four-turn dispatch campaign then passed, followed by the separate eight-turn repair campaign. Failed attempts are not capability evidence. That initial campaign covered dispatch and repairs only.

`test/functional/cli-file-workspaces.test.ts` checks the production declarations, the exact refusal messages for undeclared capabilities, and the pinned version against these retained reports. A Claude version change must update the live evidence before this regression can pass. Docker and Podman synthetic transcript tests separately cover portable capture and restoration into a fresh sandbox home. These tests never use account credentials or model calls.

At the end of the initial Claude campaign, the other four CLIs had no live file evidence. Their subsequent results appear below. Authentication modes, models and providers other than the Claude combination above were not part of this campaign.

The account owner subsequently authorized testing continuation, live input and interactive attachment. Continuation passed twenty CLI turns: initial conversation, warm resume, warm fork, fresh-container restore and fresh-container fork for each binding. Live input passed four CLI turns, each with an instruction injected during a tool call, a changed typed answer and a file containing the supplied nonce.

The final interactive campaign passed two user requests per binding, followed by normal exit, idle-session cancellation and sandbox reuse. Preliminary PTY probes exposed Claude’s onboarding/login dialog and the default refusal in its trust dialog; those failed cases do not establish support. Two earlier productive campaigns completed six user requests in total before the driver stopped on a later trust dialog. The final report records prepared onboarding and trust preferences explicitly, preserves native tool confirmations, and contains only validation metadata. No production authentication or home-configuration behavior was changed to obtain this evidence.
