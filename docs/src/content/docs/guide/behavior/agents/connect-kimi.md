`agent({ harness: kimiHarness() })` runs Kimi Code, `kimi`, through the same sandbox providers as the other adapters. Every run starts a fresh session.

## Install the CLI

Images generated by `outpost init` install the pinned `@moonshot-ai/kimi-code` package alongside Claude Code, Codex and Copilot. Remote providers bootstrap the same pinned version into `~/.outpost-tools` when needed, unless `bootstrap: false`. For `localSandboxProvider()`, install `@moonshot-ai/kimi-code` on the host yourself. `agentVersions.kimi` reports the pinned reference version.

Outpost sets `KIMI_CODE_NO_AUTO_UPDATE=1` for every `kimi` command so that the CLI does not replace itself during a run. A value in the harness `variables` overrides it.

## Authenticate

Select authentication explicitly with the harness `authentication` option. Without it, Outpost prepares nothing and `kimi` uses whatever the sandbox environment already provides. Kimi Code accepts `account`, `account.file`, `usage`, `usage.key` and `usage.variable`. See the [authentication manual](../../../manual/authentication/) for the forms shared by all agents.

### Kimi Code account

```ts
import { agent as composeAgent, kimiHarness } from "@elie-laloum/outpost";

const login = composeAgent({
  harness: kimiHarness({ authentication: "account" }),
});
const dedicated = composeAgent({
  harness: kimiHarness({
    authentication: { account: { file: "~/.outpost/accounts/kimi" } },
  }),
});
console.log(login.name, dedicated.name);
```

Run `kimi login` on the host and complete its device-code flow. `account` reads the profile in `KIMI_CODE_HOME`, otherwise `~/.kimi-code`. Unlike other agents, `account.file` names a profile **directory**, not a single file. Outpost reads two files from the profile, `credentials/kimi-code.json` and `device_id`, each a regular file of at most 1 MiB; symbolic links and directories are refused, and file contents never appear in errors. A missing file fails with its path and suggests `kimi login` or `usage` with `KIMI_API_KEY` and a model.

On Docker, Podman, Vercel, Daytona and Firecracker, Outpost writes both files to `~/.kimi-code` in the private sandbox home with mode `0600`, then runs `kimi login` inside the sandbox, bounded to 120 seconds. Because a token already exists, this login refreshes it when needed and regenerates `config.toml` with the managed Kimi Code provider, its model catalog and default model, as a host login would. The sandbox login uses the CLI's default region. Accounts signed in with `kimi login --region global` have not been validated in sandboxes.

With `localSandboxProvider()`, Outpost copies nothing and runs no login command: `kimi` uses its own host profile for `account` and `account.file`.

In account mode, `model` on `agent()` is optional and is passed with `--model`. It must be a model alias from your Kimi configuration, such as `kimi-code/<id>`.

### Moonshot API key

```ts
import { agent as composeAgent, kimiHarness } from "@elie-laloum/outpost";

const model = process.env.KIMI_MODEL;
if (!model) throw new Error("Set KIMI_MODEL to a Moonshot platform model");
const declared = composeAgent({
  harness: kimiHarness({ authentication: "usage" }),
  model,
});
const team = composeAgent({
  harness: kimiHarness({
    authentication: { usage: { variable: "TEAM_KIMI_API_KEY" } },
  }),
  model,
});
console.log(declared.name, team.name);
```

`usage` reads `KIMI_API_KEY` from the resolved workflow variables: the harness `variables`, the sandbox provider `variables` and the declarations in the repository `.outpost/.env`. `usage.variable` reads another declared variable, and `usage.key` takes a literal key, which should stay out of committed code. A missing variable fails when the sandbox is prepared with `Missing KIMI_API_KEY. Declare the selected credential explicitly.`

API-key authentication **requires** a model on `agent()`; without one, composition fails with `Kimi Code usage authentication requires a model name on agent()`. Outpost configures Kimi through environment variables only: `KIMI_MODEL_API_KEY` receives the key, `KIMI_MODEL_PROVIDER_TYPE` is `kimi` and `KIMI_MODEL_NAME` is the model name. `--model` is not passed in this mode. Kimi then uses the Moonshot platform endpoint, `https://api.moonshot.ai/v1`; set `KIMI_MODEL_BASE_URL` in the harness `variables` to use another endpoint. The same variables are forwarded on the local provider. API usage is billed to the Moonshot platform account, separately from Kimi Code plans.

### Unsupported forms and token rotation

Kimi Code has no long-lived account token, so `{ account: { key } }` and `{ account: { variable } }` fail when the agent is composed: `Kimi Code does not support account.key authentication. Accepted forms: account, account.file, usage, usage.key, usage.variable`. Invalid shapes, empty values and invalid variable names fail the same way.

The sandbox login may refresh the session and rotate its refresh token, which can invalidate the host copy and sign the host out. Keep a dedicated profile used only by Outpost, sign it in with `KIMI_CODE_HOME` pointing to it, and select it with `account.file`, for example `~/.outpost/accounts/kimi`. Do not share one profile between parallel sandboxes that refresh it independently.

## Configure execution

```ts
import {
  agent as composeAgent,
  dispatch,
  kimiHarness,
} from "@elie-laloum/outpost";
import { dockerSandboxProvider } from "@elie-laloum/outpost/providers/docker";

const key = process.env.KIMI_API_KEY;
const model = process.env.KIMI_MODEL;
if (!key || !model)
  throw new Error("Supply KIMI_API_KEY and KIMI_MODEL before running");
const result = await dispatch({
  repository: "/path/to/repository",
  agent: composeAgent({
    harness: kimiHarness({
      authentication: "usage",
      variables: { KIMI_API_KEY: key },
    }),
    model,
  }),
  sandboxProvider: dockerSandboxProvider(),
  branch: { mode: "named", name: "kimi-review" },
  brief: { text: "Review the repository and report your findings." },
});
console.log(result.text);
```

Build the generated image before this example. `model` accepts a model name only; `reasoning` and `maxOutputTokens` are rejected when the agent is composed.

A headless run executes:

```sh
kimi [--model MODEL] --prompt TEXT --output-format stream-json
```

Kimi has no stdin prompt channel, so the prompt is a command argument. Operating systems limit argument size, to about 128 KiB for a single argument on Linux, and a larger prompt fails to start: keep large context in repository files that the agent reads. Like other arguments, the prompt is visible to processes that can list the sandbox's processes. `--yolo` is not passed because Kimi rejects it with `--prompt`; prompt mode already runs without asking for approval, so tools run unattended inside the selected sandbox. Only select repositories whose project configuration you trust. Outpost's provider supplies isolation; `localSandboxProvider()` remains unisolated.

Interactive sessions run `kimi [--model MODEL]` in the CLI terminal interface. Kimi accepts no initial prompt there: an interactive request with initial text fails with `Kimi Code starts interactive sessions without an initial prompt`. They require a provider with interactive terminal support, such as Docker, Podman or local execution. See [interactive sessions](../../../environment/commands/).

## Output and failures

Events are decoded by their `role` field. `assistant` records become text observations from `content` and tool observations from `tool_calls`, with the function name, its `arguments` parsed as JSON when possible and the call `id`. `meta` records of type `session.resume_hint` report the session ID, and `turn.step.retrying` records become nonfatal warnings. Other records remain available in raw observations.

Kimi emits no final result event, so the CLI exit status decides the outcome: a zero exit succeeds and a nonzero exit fails the dispatch.

## Usage and session limits

Kimi's output reports no token counts: `result.usage` stays at zero. Track consumption in your Kimi Code or Moonshot platform account.

Kimi sessions are fresh sessions only. The emitted session ID is informational: Outpost does not capture, relocate, restore, resume or fork Kimi conversations. `result.resume()`, `result.fork()` and explicit continuations fail with `Kimi Code does not support continuation or fork in Outpost`, including within a warm sandbox. Additional passes start fresh sessions. Structured responses work with `repairs: 0`; automatic repair requires continuation and is rejected. Session resume is planned; see the [roadmap](../../../../project/roadmap/).

## Diagnose the installation

Inspect the installed CLI without model calls or credentials:

```sh
npx @elie-laloum/outpost doctor --sandbox-provider docker --agent kimi
```

The check runs `kimi --version`, reported next to the pinned reference version, and `kimi --help`, which must identify the command and declare the options Outpost uses. It does not authenticate an account or prove a live model's behavior.
